Demo Engineering How it works

qburn

Same Rust model on the CLI and in this browser demo — Burn on WebGPU, not an ONNX export.

What this is (and isn’t)

You can already run Qwen3-VL in the browser with transformers.js. That path exports the model to ONNX and lets ONNX Runtime drive WebGPU. It’s faster, more polished, and what you’d ship for a product demo.

qburn is doing something narrower: the vision tower, fusion, and language decoder are written as Burn modules in Rust. The CLI runs those modules on Metal or CUDA. The page is the same modules, compiled to wasm, talking to the browser’s WebGPU. There’s no separate “web model.”

Where the stacks diverge

qburn transformers.js
Model Rust Burn modules you can read and step through ONNX graphs exported from Hugging Face
GPU work CubeCL kernels lowered to WGSL ONNX Runtime’s WebGPU execution provider
Page glue wasm-bindgen inside a Web Worker JavaScript calling into ORT
Weights Sharded burnpacks (usually q4-mix), Cache API ONNX files with ORT’s own quant formats
Desktop twin Same crate as cargo run -p qburn Different stack from the PyTorch training code

Why bother

If the goal is “caption an image in Chrome,” transformers.js wins. This project is useful when you care whether Burn can carry a real multimodal model across the browser’s sharp edges: workgroup shared memory is often only ~32 KiB, a 2B pack has to fit wasm32 after shard concat, and turning on fusion or autotune can emit WGSL that bricks the device for the rest of the session.

Keeping one codebase also forces honesty about backends. Metal and browser WGSL are not the same CubeCL path. We compare the same burnpack on the Metal CLI, a native WGSL CLI build, and this page instead of papering gaps with prompt tricks.

What had to be true for the demo

The page runs the full instruct cascade — image patches through the vision tower, visual tokens spliced into the chat template, then the Qwen3 decoder with a KV cache — not a stub that only embeds an image. Weights are quantized for the browser: q4-mix leaves embeddings, norms, and the vision I/O path in F16 and compresses the big linear layers; plain q4 is smaller but rougher. Full fp16 packs don’t fit once expanded in wasm32.

Matmul tile sizes come from Burn 0.23’s hardware-aware planner, so kernels respect the adapter’s shared-memory limit instead of asking for desktop-sized tiles browsers reject. Prefill logit probes exist so you can tell “this quant is lossy” from “WebGPU drifted.”

Speed

Expect this demo to be much slower than transformers.js for a short caption — often on the order of a minute. That’s a real limitation, not a temporary demo quirk. Use the CLI when you want throughput; use the page when you want to see the Burn path survive in a browser.
