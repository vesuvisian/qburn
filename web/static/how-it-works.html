Demo Engineering How it works

qburn

How an image and a prompt become caption tokens — in the CLI and in this WebGPU demo.

qburn implements Qwen3-VL-2B-Instruct as Burn modules. An image is turned into visual tokens, those tokens are spliced into the chat template, and the language model generates text. The browser build is the same cascade compiled to wasm. 

image  →  patches  →  vision tower (+ DeepStack)
prompt →  tokenize →  chat template with image-pad slots
                      ↓
         replace pads with visual rows → decode tokens

Model shape

The 2B instruct preset matches upstream config.json (Qwen3VlConfig::qwen3_vl_2b()):

Part Size
Language model hidden 2048, 28 layers, 16 heads / 8 KV heads, head dim 128, MLP width 6144, vocab ~152k
Vision tower 24 layers, hidden 1024, 16 heads, 16×16 patches, temporal patch 2, spatial merge 2 → 2048-d visual tokens
DeepStack Extra features from vision layers 5, 11, and 17 are added into early decoder residuals
M-RoPE 3D rotary sections [24, 20, 20], rope_theta=5e6, interleaved layout

From pixels to patches

ImageProcessor in crates/qburn/src/vision/preprocess.rs decodes PNG, JPEG, or WebP, then resizes so both sides are multiples of 32 (patch size × spatial merge). Total pixels stay inside a [min_pixels, max_pixels] band. RGB is scaled roughly into [-1, 1].

Qwen3-VL expects a temporal pair, so the frame is duplicated, then cut into patches in merge-block order. Each patch is 3×2×16×16 = 1536 values. After the vision merger, the model sees grid_t × (grid_h/2) × (grid_w/2) visual tokens. The chat template inserts that many <|image_pad|> slots between vision start/end markers.

Vision tower

VisionEncoder follows the Hugging Face Qwen3VLVision* layout. The checkpoint stores patch embedding as a Conv3d [1024, 3, 2, 16, 16]; at load we flatten that into a Linear [1536, 1024] plus bias.

Absolute positions come from a learned 48×48 grid (num_position_embeddings=2304), bilinearly resampled to the image’s patch grid (align_corners=True). On wasm that table is built on the CPU via into_data_async. Patches also get 2D rotary embeddings with interleaved height/width frequencies. Each block is LayerNorm → attention → GELU MLP with residuals. A spatial merger groups 2×2 patches and projects them to the language width (2048). DeepStack runs extra mergers at the configured layers and scatters those features onto the image-pad positions later in the decoder.

Splicing vision into text

build_multimodal_embeddings embeds the token ids as usual, then overwrites each image-pad position with the matching visual row. Position ids are 3D (time, height, width) over the vision grid, then continue along the text. MRopeEmbedding turns those into cos/sin tables for the attention layers. Later decode steps that only add text reuse a cheaper 1D RoPE table where all three axes match.

Language decoder

TextDecoder is a dense Qwen3 stack: RMSNorm, fused QKV with QK-Norm, grouped-query attention, and a SwiGLU MLP with fused gate/up projections. Each layer keeps a KV cache so decode steps only attend with a single new query. Prefill still uses a causal mask; decode does not rebuild one.

When the HF config ties embeddings, lm_head shares the embed matrix. Burn’s Linear wants [hidden, vocab], so the tied copy is transposed from the [vocab, hidden] embed. Temperature ≤ 0 is greedy argmax; above 0 we scale logits, softmax, and multinomial-sample with getrandom. Both CLI and wasm stream one token id at a time and stop on <|im_end|>. With --probe (or ?probe=1 on the page) the first prefill step dumps its top-10 logits for Metal vs WebGPU checks.

Weights

qburn-converter (crates/converter) loads Hugging Face safetensors into Burn modules, optionally quantizes, writes a burnpack, then splits it into .bpk.part shards listed by manifest.json. Flag details are in the repo README. 

HF safetensors → Burn modules → quantize → .bpk → .bpk.part + manifest.json
Mode What you get ~Size (2B)
fp32 Full precision resident tensors ~9 GiB
fp16 Stored F16, loaded as F32 ~4.5 GiB
q4 Uniform Q4S, block 32, F16 scales ~1.3 GiB
q4-mix Q4S on large linears; embeds, norms, vision I/O stay F16 ~1.8 GiB

q4-mix is asymmetric post-training quant with Burn’s MinMax only (no AWQ/GPTQ). Embeddings, every norm, vision patch/pos/merger/DeepStack, and linear biases stay F16. Decoder QKV, output, SwiGLU, and vision-block linears go Q4S. lm_head may be stored quantized and re-tied from the float embed on load.

Keeping the whole ViT in F16 plus a float embed blows past the ~2 GiB wasm32 ceiling when shards are concatenated, so vision blocks stay Q4S in the browser pack. Prefer q4-mix for quality; use uniform q4 if you need the smaller download. The page pre-sizes the concat buffer from the manifest byte count — letting a Vec amortize growth on a ~1 GiB pack can overflow wasm32. Parts are cached with the Cache API. Weights are not in git; Pages CI rejects files ≥100 MB.

Browser path

index.html / demo.js
        │ postMessage
        ▼
   worker.js  →  pkg/qburn_web.js (wasm)
                   init WebGPU, fetch shards, stream tokens
        ▼
   caption area

Inference runs in a Web Worker (web/src/lib.rs). WebGPU is acquired with Device::wgpu_options().graphics_api(WebGpu).init_async() before any weight download, so unsupported browsers fail fast. Fetches use WorkerGlobalScope — web_sys::window() is null in the worker. Shards are concatenated to the manifest size, loaded as one burnpack, and the device stays in app state for describe.

On wasm, argmax and vision pos-embed sampling go through into_data_async; the CLI blocks the same futures with pollster. The demo caps preprocess at 262 144 pixels (the CLI allows ~1 M), fetches shards in parallel, skips causal masks on single-token decode steps, and only runs the prefill probe when the URL has ?probe=1. Prefill writes vision and DeepStack features in one contiguous assign; absolute pos tables are cached after the first image.

WebGPU matmul

Burn 0.23 + CubeCL 0.12-pre pick matmul tiles with a hardware-aware planner (MatmulKernelHeuristic::Tile) against max_shared_memory_size. Browsers are often around 32 KiB. Older Burn 0.22 paths asked for ~72 KiB tiles and needed a forced Naive override; that patch is gone.

A small cubecl-runtime patch under patches/ keeps the wasm build compiling (upstream gates tune::sampler off wasm but still calls it). Autotune stays off for the web crate — a bad candidate can emit invalid WGSL and poison the device. Fusion is also off on the webgpu feature; fused kernels were a suspected cause of greedy collapse in the browser versus Metal on the same q4-mix pack. On macOS the default desktop wgpu feature often rides Metal; for a WGSL control build use --features webgpu,cli.

Native Metal is still a different CubeCL runtime than browser WGSL. Captions and speed will diverge even on one burnpack. Don’t hide that with prompt or loop hacks.

The page always loads burnpacks (Hub by default, or python3 web/preview.py --weights DIR). The CLI can also open a raw HF safetensors checkout. Local preview uses a threaded HTTP server so multi-hundred-megabyte shard GETs don’t freeze the SPA. There is no CPU fallback for this model in the UI.

Checking parity

When a caption looks wrong, separate quantization loss from backend drift. Same image, prompt Describe this scene., temperature 0, with --probe:

CLI + weights/burnpack-q4 on Metal Uniform q4 vs HF
CLI + weights/burnpack-q4-mix on Metal Mix quant vs HF / q4
CLI --features webgpu,cli + same pack Native WGSL, no fusion
This page + same q4-mix pack Browser WebGPU 
cargo run -p qburn --release --no-default-features --features metal,cli -- \
  describe --model weights/burnpack-q4-mix --temperature 0 --max-tokens 64 --probe \
  path/to/photo.jpg

Merge-token counts should match. Prefill top-10 logits should be close when Metal and no-fusion wgpu land on the same GPU API; browser WebGPU can still drift — check the worker console for prefill probe:. q4-mix should track HF better than uniform q4.

For numeric dumps, scripts/dump_logits_ref.py writes an HF reference under tests/parity/. Config and preprocess unit tests live next to the crate; CLI flags are in the README.
